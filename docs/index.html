How a run works

  1. Freeze the testAuthor a Kane testmd once at a good commit. Its step recordings are copied and never change.
  2. Bisect with replaysEach probe: fresh checkout, app started, frozen test replayed headless. Replays reuse recordings, so a probe takes seconds.
  3. Name the culpritThe boundary pair is confirmed twice. Any disagreement is reported as inconclusive, never guessed.
  4. Fix and prove itRevert (or an agent patch), then replay the same recordings at the fixed commit.

Why the answer can be trusted

  • Healing is off.Adaptive healing could rewrite a broken step into a pass, so every probe runs with --no-adaptive-heal.
  • Errors never become blame.A Kane error or timeout is a skip. Culprit aborts rather than accuse a commit.
  • The test cannot be weakened.A fix commit that touches the test bundle is rejected.
  • Replay is proven stable first.Gate 0 replays the test 10 times on each side before any bisect is trusted.

What is and is not proven

The demo history is seeded (16 commits, one planted regression). The agent-patch fix is tested only against a stubbed API. The explorer replays recorded verdicts and cannot run Kane for you, because Kane needs a logged-in CLI and Chrome on your machine.

Questions

What does Culprit do?

When a recorded browser test starts failing, it finds the commit that broke it, reverts that commit, and replays the same test to prove the fix. It searches history by bisection, so it needs about log2(n) probes instead of walking every commit.

How is this different from git bisect?

It is the same idea applied to browser flows. Each probe replays a recorded Kane test against a fresh checkout. Culprit adds the parts that make a browser result trustworthy: healing off, errors treated as skips, a double-checked boundary, and a guard on the test files.

Why turn adaptive healing off?

Healing can re-author a failing step so it passes. In a bisect that could turn a real regression into a false “good” commit, so every probe runs with --no-adaptive-heal.

What if the test is flaky?

Gate 0 replays the test 10 times at the good commit and 10 at the bad one before you trust anything. On the demo test the result was 10/10 and 10/10. During a run the boundary pair is confirmed twice, and any disagreement is reported as inconclusive instead of guessed.

What happens if Kane errors or times out?

That probe is a skip, never “bad”. If the error is at a known endpoint, the run aborts and tells you why. A broken environment never gets blamed on a commit.

Does an AI write the fix?

By default no: the fix is a git revert of the culprit, re-verified with the same frozen recordings. An optional agent mode asks a model for a small patch. It has only been tested against a stubbed API so far, and a fix that touches the test files is rejected.

Is the demo real or staged?

The Kane results are real, from Nov 16, 2026. The repo history is seeded: 16 commits with one planted regression, labelled as such. The explorer page replays those recorded verdicts and its slider is a labelled simulation.

Does it cost Kane credits?

Authoring the test once uses credits. Replays reuse the recordings, and the Luma page says cached replays are free. We have not audited the credit balance after the Gate 0 run, so check yours.

Can I use it on my own repo?

Yes, from the command line: one test file and one app start command per run, on a history where the regression is monotonic (good, good, bad, bad). The hosted pages cannot run Kane for you.
