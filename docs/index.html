Which commit broke checkout?

When a code change quietly breaks your checkout, Culprit finds which one. It replays a recorded browser test on your past commits, pinpoints the one that broke it, undoes it, and checks that checkout works again.

How it works

  1. Record the test onceKane records a browser test on a version that works. That recording never changes.
  2. Search your historyCulprit jumps through your commits, halving the range each time, and replays the test on each one. A replay takes seconds.
  3. Name the culpritIt double-checks its answer. If the checks disagree, it says “inconclusive” instead of guessing.
  4. Fix it and prove itIt undoes the bad commit, then replays the same test to show checkout works again.

Why you can trust the answer

  • No self-healing.Kane can auto-repair a broken test step, which could hide a real bug. Culprit turns that off.
  • Errors never get blamed on a commit.If Kane glitches or times out, Culprit skips that check or stops. It never accuses a commit because of an error.
  • The test can't be weakened.A fix that edits the test is rejected.
  • Checked for flakiness first.Before searching, the test is replayed 10 times on the good version and 10 on the broken one.

Questions

What does Culprit do?

When a recorded browser test starts failing, it finds the commit that broke it, undoes that commit, and replays the same test to prove the fix. It searches by halving the range each time, so 15 commits take about 4 checks instead of up to 15.

How is this different from git bisect?

Same idea, applied to browser flows. Culprit adds what makes a browser result trustworthy: self-healing off, errors never blamed on a commit, a double-checked answer, and a guard on the test files.

Why turn off self-healing?

Self-healing can quietly rewrite a failing test step so it passes. During a search, that could make a broken commit look fine and send Culprit to the wrong answer.

What if the test is flaky?

Culprit replays the test 10 times on each side first. On the demo test that was 10 passes and 10 failures, with no errors. During a search the answer is checked twice, and any disagreement is reported as inconclusive.

What happens if Kane errors or times out?

That check is skipped, never counted as “bad”. If it keeps happening, the run stops and tells you why. A broken environment never gets blamed on a commit.

Does an AI write the fix?

By default no: the fix is a plain git revert of the culprit, re-checked with the same test. An optional AI mode can propose a small patch, but it has only been tested against a fake API, and any fix that edits the test is rejected.

Is the demo real or staged?

Both, and labelled. The Kane results are real, from Nov 16, 2026. The commit history is made up, with one planted bug. The Real run page replays those recorded results, and its slider is a labelled simulation.

Does it cost Kane credits?

Recording the test once uses credits. Replays reuse the recording, and Kane's event page says replays of a recorded test are free. I haven't checked my balance after the reliability check, so check yours.

What does the “Try it live” button run?

Culprit's real search, undo and verify steps, on the made-up 16-commit history, live on this server. Only the browser replay is a stand-in.

Can I use it on my own repo?

Yes, from the command line. You need one test file and one command that starts your app, and a history where commits go good, good, bad, bad (the bug stays once it appears). The hosted page only runs the demo, so run the CLI locally to use real Kane.
